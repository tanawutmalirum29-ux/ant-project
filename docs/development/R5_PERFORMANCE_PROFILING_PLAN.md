## 2. What actually runs

- SOURCE FACT — src/core/time.js:1-4,30-53: fixed tick = 100 ms, 10 ticks/second at x1; supported speeds 0/1/2/4; clock advances 0.3 **in-game minute** per tick. Game.update(realDeltaMs) clamps input to 250 ms, accumulates speed-scaled time, executes up to 32 fixed ticks; pause speed=0 does not execute systems. Thus **30 game minutes = 100 simulation ticks**, regardless of speed. With repeated update(100): at x1 100 calls, x2 50, x4 25; pause runs 0 ticks. These counts are scheduling mathematics, not CPU results.
- SOURCE FACT — src/core/game.js:9-40: fixed system order Colony.tick -> Foraging.tick -> Rooms.tick -> Lifecycle.tick -> Combat.tick. A future optimization MUST preserve this ordering and the clock/tick semantics; isolated system benchmarks supplement but do not replace Game.update measurements.
- SOURCE FACT — src/world/generate.js:9-19,77-88: surface 128×128 (16,384 cells), underground 96×64 (6,144 cells), each using Uint8Array. Paired portal entry points are explicit.
- SOURCE FACT — src/world/navigation.js:23-65: findPath builds fresh g Float64Array, prev Int32Array, closed Uint8Array and an A* heap **per call** on a cardinal walkable grid. reachablePaths:69-90 builds fresh dist, prev and queue Int32Arrays and BFS **per call**; reconstructed path arrays are additional allocations.
- CALCULATED — one reachablePaths call against the underground grid creates at least 3 × 6,144 × 4 = **73,728 bytes (72 KiB)** of Int32Array storage, without JS objects, allocation metadata or GC. If run for 16 rooms, this is **1,179,648 bytes per tick** (1.125 MiB), and at ten ticks/s **11.25 MiB/s** of such array storage. At 32 rooms it is **2.25 MiB/tick** or **22.5 MiB/s**. Those are theoretical allocation quantities, **not observed heap/RSS/GC or execution latency**. TypedArray backing store may show up in arrayBuffers/external, not only heapUsed.
- SOURCE FACT — src/main.js:33-59: requestAnimationFrame invokes game.update(dt), then renderer.render **every animation frame**; UI.updateMetrics and CombatControls.update run at most once per >150 ms check (not every tick). Node CPU and browser render/DOM work must be measured separately.

### Structural call graph details and ownership
- Room status can change in Rooms.updateConnectivity itself, Rooms.queue/cancel/advance, and Rooms.onWorkerDeath. Lifecycle.killWorker can invalidate a builder and the queen's survival. This is a **state** change even if terrain stays identical.
- Colony.chooseOrder uses queued-job insertion order and ties by job.id; cache/priority-queue designs must not silently alter selection, ownership or job progress.
- Foraging.walk and Combat.walk move one cardinal tile per actual step or transfer via the real paired portal. Reusing a route must still validate each pending step against actual walkability and interrupted actions; a cached path **cannot imply** teleportation.
- Rendering already culls by visible tile bounds; “currently renders entire world each frame” would be false. Measure visible tile count, zoom and Canvas command count, not just world A.

## 4. Topology writer / cache invalidation audit

| Mutation source | When and how | Existing safe signal | What proposed caches must handle |

| Rooms.queue/cancel/advance/onWorkerDeath | Room list, material reservations, statuses, workerId, stock, readiness/connected effects | **no global revision; room identity/status/stock changed** | Per-tick shared BFS may be reused for geometry only; placement/delivery/worker/stock decisions must read live room state and cannot be frozen in the topology cache |
| Lifecycle.killWorker / queen alive flag / Combat damage | Death, transfer of order/cargo/reservations, possible queen death | **live workers/queen.alive** | Invalidate routing origin/room benefits on queen death; invalidate eligibility/reservations on recruit/demobilize/death; do not reuse dead worker or ownership maps |
| Foraging pick/deposit, Lifecycle.consume, Rooms.reserve/take/cancel | Source reservations and available stocks change **without terrain changes** | **live stock/inventory/reservation fields** | Do not use colony.completed to cache source availability, room capacity or resource mass |
| src/ui/app.js / src/main.js reset, select layer, camera motion | Seed reset reconstructs Game; camera pan/zoom/layer changes visible world and display | **Game/world identity, camera layer/position/zoom, canvas size/DPR** | Renderer tile caches must include layer, terrain revision (where supported), visual settings and viewport; invalidate on resize/layer/reset; no stale clickable coordinates |

**Invalidation conclusion:** colony.completed is sufficient **only for ordinary successful excavation additions** in current gameplay. It is not a universal terrainRevision, does not track direct writeCell, does not encode room stock/readiness, queen death, active jobs, camera or workers. Therefore **top Stage-1 proposal uses one fresh shared underground BFS per Rooms.tick**, not a cross-tick memo, preserving the present “always recheck connectivity next tick” behavior while removing R redundant BFS traversals. The proposed BFS must be constructed after Colony.tick in each tick, then used by all room connectivity checks that tick; invalid origin/queen death must still disable rooms promptly. Rooms.validate invoked independently during render or on click needs its own fresh result, unless verified same-state cache semantics are later authorized. Avoid hiding synthetic terrain-obstruction tests.

## 5. Deterministic benchmark matrix and fixtures — proposed, NOT RUN

|---|---|---|

| Combat events E | **0, 10, 100** *cumulative scripted attack/interception interactions over the measurement episode* | NOT 100 simultaneous enemies: COMBAT.maxEnemies = 5. Schedule deterministic spawn/retreat/attack opportunities; record real successful engagements versus scripted attempts |
| Speed | **0, 1, 2, 4** | Measure scheduler separately from normalized per-simulation-tick costs; pause requires zero steps and unchanged simulation snapshot |
| Seed | At least **3** named seeds, e.g. ANT-001, R5-PERF-B, R5-PERF-C | Stable seed strings; save the actual generated world/hash and manifest |

| Rendering overlay | no DOM updates / normal HUD + tactical panel + continuous room preview | Browser only; Node baseline excludes DOM and Canvas |

### Fixed-step / time budget protocol
- Target exactly **100 executed fixed ticks = 30 in-game minutes** at speeds 1/2/4. With update(100) nominal call counts x1=100, x2=50, x4=25; measure both per Game.update call and amortized **ns per executed tick** (time before/after each update divided/attributed by actual returned step count). Pause speed=0: issue 100 update(100) calls with **zero** simulated ticks; report ns per call only; per-tick latency is N/A, not zero.
- For scheduler burst sensitivity additionally measure dt sequences [16.67, 33.33, 100, 250, 1000] ms; fixed-step clamps to 250ms. Log actual step counts, dropped accumulator, clock advance. No renderer on Node path.
- Warm-up JIT separately: e.g. 200 Game ticks per seed/fixture **before** warm recorded window; avoid timing world/fixture setup. Cold first 100 ticks and warm subsequent 100 ticks represent different game states, **not** directly apples-to-apples optimization comparisons; compare baseline vs optimized at identical event positions for each window.
- Repetition **proposed:** 5 untimed rehearsal runs, >=20 measured repeats for screened cases, >=30 for finalist worst-case cases, across >=3 seeds; randomized or ABBA process ordering with independent processes and identical hardware. Samples measured at fixed tick boundaries; record raw timings, no selective outlier deletion. Report p50, p95, p99, mean, max, standard deviation and confidence intervals (bootstrap across independent scenario replications; account for repeated ticks not being independent).
- CPU time: process.hrtime.bigint() for whole update and separate module sections; log both inclusive and exclusive costs to avoid double-counting nested Rooms.assign/findPath. Memory: process.memoryUsage().heapUsed, heapTotal, rss, arrayBuffers and external before/after setup and window; peak sampled at intervals and allocations/GC collected separately via inspector or allocation profiler. Optional --expose-gc only **between** replicates and identically in both versions, never during timed tick windows. Record GC count/pause with separate profiler run (profiling overhead affects comparisons).
- Output planned machine-readable JSON/CSV: baselineSHA, candidateSHA, environment, seed, fixture manifest, tickIndex, speed, executedTicks, elapsedNs, subsystemNs, findPathCalls, reachablePathsCalls, ensureFormationCalls/actualRebuilds, pathsExpanded/peakQueue (if instrumented), heapUsed/arrayBuffers/rss, GC, coldWarm, expected/actual gameMinutes, fixture validity, exit code. ## 6. Exact replay, correctness and gate protocol

Construct independent baseline and optimized Game instances from the **same seed, exact fixture construction event log and tick-ordered commands**. Never share mutable objects between runs. Freeze event schedule (including external queue/cancel, room selection, seed reset, soldier recruiting and deaths) and apply at the same pre-tick boundary. Compare every tick or a chosen reproducible cadence, and always at episode end:

- clock ticks, game time, speed, pause snapshot; system tickCount. No simulation progress under pause; changes to UI state/camera during pause are allowed but game state must remain unchanged.
- worker IDs/castes/role, (layer,x,y), facing, next/path/motion, state, orderId and ownership; cardinal or paired-portal transition only, no off-path position jump; abandoned miner cannot clear someone else's job.
- ordered job IDs, status/progress/workerId; completed digs and exact underground terrain Uint8Array hash; room ID, type, footprint, progress, status, connected, assigned worker, pickups and recovery state.
- resource **per type**: source amounts, source reservations (not counted twice), worker cargo, local room stock, aggregate inventory, rooms.held, rooms.spent, lifecycle.consumed/lost, including explicit fixture injections. Mass balance must equal the opening ledger plus documented injections; temporary held stock must not disappear or be duplicated.
- brood stages, age, care, carrier/target-room ownership, births and deaths, queen alive/health, nurse slots and actions; forager reservations and delivered trip count.
- combat soldier ID roster and unique nullable formation goals/status, deterministic slot selection, same-center motion reset, destination bounds R8/D12, enemy positions/type/HP, damage/cooldowns, portalCrossings, ralliedCount only during rally, actual retreat/healing and threat priority.
- same random generator sequence / spawn occurrence, where available; replay twice on identical build to validate deterministic test harness itself before comparing versions.
- room connectivity disconnected/reconnected mid-route, dead worker while carrying supplies, cancellation/refund, stock-full reroute, blocked pending step, new dig opening previously unreachable goal, rapid recruit/demobilize, 0/150 worker boundaries.

Assert key invariants on every replayed tick. **Rollback immediately** on any divergence in inventory mass, owner ID, queued order, terrain, cardinal step/portal, combat HP/damage, deterministic goal, clock, pause, or disconnected storage behavior.
